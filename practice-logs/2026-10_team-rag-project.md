## 使用的文件

**Library**：项目总览、范围与验收、GitHub 协作规则、沟通规范、MVP 技术方案、链接索引、企划书回填清单、评测方案、工作方式，以及定稿后的模块地图

**项目记忆**：决策记录（5 天内拆到 6 份）、当前状态（2 份）、小约定（简报格式、编号写法、称呼、成员账号等）

**外部事实来源**：GitHub Issues

**没有放进项目的**：有已知错误的发表 PPT、还没填完的企划书原文、课程的 50 页 Git 教程（只提取了规则部分）

## 有效的做法

- 新建项目前先交叉核对全部文件，一次修掉了编号撞车、和已定决策冲突、过时内容等问题
- 决策权限表：让 PM 不用对每个实现细节拍板
- 【记录】→ 用户确认 → 写进决策记录：结论不再散落在聊天里
- 长期讨论串的第一个任务用真实的小任务，当天就产出了可用的结果
- 每日简报定时任务：用户每天早上直接看简报、转发群消息
- 一次性的大任务单独开讨论串，避免占用协调器的上下文

## 遇到的问题（协调器复盘，已归纳）

- 第一次写记忆时把占位符原样发出去了
- 记忆文件约 4KB 上限，长表格被拆成多份
- 协调器在讨论串核对源文件之前就起草了对外消息，两边结论冲突
- 协调器凭记忆汇总进度，漏掉讨论串的最新结果
- 群消息草稿沿用了已被推翻的分工
- Issue 和 PR 编号混用，看不出"#N"是哪种
- 成员不是仓库协作者，无法分配 Issue 和审阅人
- PR 作者不能批准自己的 PR；"Related to"不会关闭 Issue
- 给组员的消息引用了他们看不到的项目文件
- 群消息太长；草稿里的具体时间点发出时已过期
- 用户转发外部消息时带上了 API key
- 有依赖关系的 PR 一个卡住，后面全部顺延
- 讨论串的"等你处理"状态在事情做完后仍然显示
- "到某个时间再查"的口头约定没有执行，讨论串不会到点醒来
- 协调器被替换过一次，新的只拿到摘要
- Library 的 Replace 找不到（不在右键菜单里）；下载后文件名被改，上传变成两份
- 写进文件的审阅分配一开始没通知组员

## 做过的调整

- "先提方案再开讨论串"改成只对临时讨论串适用
- 简报加上"被谁卡住"和"未确认的【记录】"
- 每周五把做完的讨论串标为已完成
- 审阅人批准后由审阅人直接合并；Issue 只用一个"阻塞"标签
- 技术问题让成员直接在 Issue 里找负责人，不经过 PM
- 企划书中 PM 负责的回填项延后到 MVP 之后，优先完成 MVP
