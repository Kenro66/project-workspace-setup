# 文件和记忆的设计

## 1. 内容放在哪

| 放在哪 | 放什么 | 谁更新 | 多久更新 |
| --- | --- | --- | --- |
| Library（用户上传的文件） | 基本不变的：总览、范围与标准、规则、参考资料、链接索引、工作方式 | 讨论串改好，用户 Replace | 有变化时 |
| 项目记忆 | 经常变的短内容：《决策记录》《当前状态》、小约定 | Claude 写，用户确认 | 随时 / 每周 |
| 外部事实来源 | 每天在变的：任务、日程、申请进度 | 相关的人 | 每天 |
| 《链接索引》 | 项目读不到的资料的位置和版本 | 用户 | 有新资料时 |

## 2. Library 文件（一般 6–10 份）

| 文件 | 放什么 | 多久变一次 |
| --- | --- | --- |
| 《项目总览》 | 目标、最终交付、相关的人（中外文名、称呼）、里程碑、决策权限、用户的工作方式、**文件与编号说明** | 很少 |
| 《范围与标准》 | 做什么、不做什么、每一项"怎么算完成"（写在结果层面，不写到实现细节）、术语定义 | 范围变化时 |
| 规则类（例如《协作规则》《沟通规范》） | 固定规则、模板、术语对照表 | 很少 |
| 参考类（例如《技术方案》） | 做事需要的背景资料 | 定稿后偶尔 |
| 《链接索引》 | 名称、用途、链接、版本、**是否最新**、**内容是否已放进项目** | 有新资料时 |
| 《工作方式》 | 用户每天、每周怎么用这个项目：什么事在哪做、按什么顺序 | 流程变化时 |

每份文件第一行写"最后更新：日期"。

## 3. 项目记忆

| 记忆 | 放什么 | 怎么更新 |
| --- | --- | --- |
| 《决策记录》 | 表格：日期｜来源｜内容｜理由｜影响谁；末尾单列"待决事项"。冲突时以它为准 | AI 在回答末尾列出【记录】，用户回"确认"后按原文追加；没确认的列在每日简报末尾 |
| 《当前状态》 | 当前阶段、下一步、本周重点、已知风险 | 每周由进度类讨论串更新，用户确认后写入 |
| 小约定 | 简报格式、编号写法、称呼、外部账号等 | 用户说"记住……"时写入 |

每个记忆文件约 4KB 上限，按"第 N 部分"拆分，索引写清楚顺序和追加位置。

## 4. 外部事实来源

任务、日程、申请进度放在专门的系统里（GitHub Issues、日历、表格），讨论串去那里读，不复制进项目。甘特图、进度报表都从这里生成。

## 5. 命名和编号

- 文件一律用名称指代（《范围与标准》），不用 F1、F2 这样的编号。原因：资料里本来就有的编号（功能编号、指标编号、问题编号）很容易和文件编号撞车，AI 会混淆含义
- 项目里出现的所有编号（用户故事、指标、决策、问题、接口格式等），在《项目总览》末尾用一张"编号说明"表写清含义和定义在哪
- 同一个字母前缀只表示一种东西。撞车时改前缀（例如确认问题从 M1 改为 CQ1，避开评测指标 M1）

## 6. 不放进项目的

- 过时的草稿、有已知错误没改的资料（例如发表用的 PPT）
- 还在变的原文（等到真正要用时，再导出最新版放进去）
- 教程类长文档（只提取规则部分）
- 密钥、密码、他人的敏感个人信息
- 讨论过程

这些在《链接索引》里登记：在哪、什么版本、是否最新、为什么没放进项目。

## 7. 资料从旧对话迁移过来时

- 让旧对话只输出已定结论，不确定的标【待确认】
- 旧对话很长时，早期内容可能已被压缩，【待确认】的地方要用户核对
- 迁移后的旧对话只作归档，不在里面继续工作
