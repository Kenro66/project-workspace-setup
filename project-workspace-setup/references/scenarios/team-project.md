# 场景：团队项目（用户是 PM）

状态：已实践（2026-10，5 人大学课程项目，见仓库 `practice-logs/`）

## 适用情况

用户负责协调一个多人项目，自己不一定懂全部技术；团队用 GitHub 协作；有老师、助教或外部导师要沟通；截止日期密集。

## 文件结构

**Library**

| 文件 | 内容 |
| --- | --- |
| 《项目总览》 | 目标、交付物、成员与职责（中外文名）、老师和外部联系人的称呼、里程碑、决策权限、催交规则、PM 工作方式、文件与编号说明 |
| 《范围与验收》 | 优先级 / 范围 / 阶段三套说法的定义和对应关系；范围表（做 / 以后做 / 不做及原因）；每个模块在用户可见层面的验收标准 |
| 《协作规则》 | GitHub 流程、审阅分配、Issue 写法与样例、PR 正文要求、AI 使用记录要求 |
| 《沟通规范》 | 对老师、助教、导师、组员的语气、称呼、署名、术语对照表、输出格式 |
| 《技术方案》 | 架构、流程、接口概要；开头注明以代码为准 |
| 《链接索引》 | 读不到的资料的位置和版本 |
| 其他（按需） | 评测方案、课程交付物的待回填清单 |
| 《工作方式》 | PM 每天、每周怎么用这个项目 |

**项目记忆**：《决策记录》《当前状态》、小约定（编号写法、称呼、成员 GitHub 账号等）

**外部事实来源**：GitHub Issues（任务、负责人、截止日期）

## 讨论串

| 讨论串 | 负责 |

## 团队规则（写进《项目总览》，并发给成员）

**决策权限**

| 影响范围 | 谁决定 |
| --- | --- |
| 只影响自己的模块 | 负责人自己定，写进 PR 或 Issue |
| 影响其他人的接口或数据 | 相关的人一起商量，定完告诉 PM |
| 影响范围或截止时间 | PM 决定 |

这张表能让 PM 从"每个实现细节都要拍板"里解脱出来。成员拿实现细节来问时，PM 回一句"按决策权限，你和某某定就好"，必要时附一个默认方案，免得对方不想决定、又把问题推回来。

**催交规则**

| 情况 | 做法 |
| --- | --- |
| 到期前 1 天 | 提醒 |
| 逾期当天 | 私聊确认：卡在哪、什么时候能交、需不需要帮助 |
| 逾期 1–2 天，或已卡住别人 | PM 决定：缩小范围、找人协助或调整顺序 |
| 反复逾期 | 周会上透明讨论，记入决策记录 |

规则提前定好并公开，执行时就不显得针对某个人。

## GitHub 设置（建仓库当天）

- 邀请成员当协作者（否则不能分配 Issue 和审阅人），同时给 main 开分支保护：必须通过 PR、必须有审阅、给管理员留绕过权限；仍然走 Fork + PR 流程
- 放 PR 模板：关联 Issue（`Closes #N`）、变更目的、验证结果、需要审阅的点、AI 使用记录（AI 做了什么、本人做了什么、本人验证了什么）
- Issue 模板：负责人、截止、范围、完成条件、不包含、依赖（写清上下游）、范围变更记录
- 完成条件的写法：写结果不写动作；别人能复现；至少一条失败情况；涉及别人模块时写明谁验证；"不包含"必须写
- 审阅分配提前定好（例如前后端互审），并告诉全组

## 验收

- 验收标准写在用户能看到的结果层面，PM 不用懂实现也能验
- 代码层面的检查交给组员互审 PR
- PM 只问三个问题：做完没？卡住没？会不会影响别人或时间？

## 课程项目特有的注意点

- 课程如果要求 commit 用本人账号、如实记录 AI 参与，项目指令和 PR 模板里都要体现
- 课程交付物（企划书等）里还没填完的部分，用一份"待回填清单"管理，不把还在变的原文放进 Library
- 截止前一两天才拼接的项目最容易出问题：先用最简方案跑通整条链路，再分头优化
