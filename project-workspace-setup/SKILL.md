# 搭建和维护 Claude 项目

本 skill 帮用户把一项长期工作搭成一个新版 Claude 项目，并设计好之后怎么维护。内容来自真实实践，每次实践后都会更新（见仓库的 CHANGELOG）。

## 开始前先做两件事

1. **核对产品事实**。新版项目还在测试阶段，按钮、限制、默认值都可能变。涉及具体操作时，先读 `references/product-facts.md`，再对照官方文档 https://code.claude.com/docs/en/claude-projects.md 。两者不一致时，以官方文档和用户看到的界面为准，并告诉用户哪里变了。
2. **分清两种"项目"**。旧版项目（claude.ai 聊天或 Cowork 里的）只是一组对话加参考文件，没有协调器。本 skill 针对新版项目；用户如果用的是旧版，下面的核心原则和文件设计仍然适用，但讨论串和协调器相关的部分不适用。

## 核心原则

搭建和维护时始终遵守这些原则：

1. **对话是工作台，文件才是记忆**。协调器只看最近的消息和项目记忆，讨论串会压缩上下文，协调器还可能被整个替换。所有要长期保留的东西，包括口头定下的小约定，都写进项目记忆或 Library 文件。
2. **按变化频率存放**。基本不变的放 Library；经常变的（决定、当前状态、小约定）放项目记忆；每天都在变的（任务、日程、进度）留在外部系统（GitHub Issues、日历、表格），不复制进项目。
3. **同一个事实只放一处**。Library 和记忆不重复存；文件之间不重复写同一段内容，用"见《某文件》第几节"代替。
4. **冲突规则事先写死**。《决策记录》优先；同一事项以日期最新的为准；聊天说法与文件冲突时，指出来问用户，不自行假设。
5. **只写已定结论**。不确定的标【待确认】，不写讨论过程。
6. **文件用名称指代，不用编号**。编号容易和资料里原有的编号撞车。项目里所有编号的含义集中写在一张"编号说明"表里。
7. **过时、有错、还在变的资料不放进项目**。只在《链接索引》里登记位置、版本、是否最新。
8. **生成物不是维护对象**。甘特图、阶段存档、审阅报告按需生成，不手动维护。
9. **规则要告诉人，不只是告诉 AI**。写进文件的团队规则，要另外发给相关的人。
10. **用户不亲手改文件**。让负责的讨论串改好，用户只负责确认和上传。
11. **给人看的消息和给 AI 看的文件分开写**。发给别人的消息不引用内部文件（对方看不到），只写要做什么、看到什么算完成。
12. **要定时做的事设成定时任务**。讨论串不会自己到点醒来。

## 搭建流程

按顺序带用户做。每一步都尽量给出可以直接复制的文字。

### 第 1 步：了解需求

问用户（最多问一轮）：

- 要达成什么、最终交付什么、关键日期
- 涉及哪些人，各自的称呼和语言
- 每天在变的东西放在哪个系统里
- 要连哪些外部工具，哪些操作必须先问用户
- 用户每天打算花多少时间，用什么语言工作
- 已有资料在哪里、是不是最新的

用户的场景如果和 `references/scenarios/` 里的某个相近，读那一份作参考。标了"未实践"的场景只是建议，要和用户一起确认。

### 第 2 步：设计文件和记忆

读 `references/file-design.md`，确定：Library 放哪几份文件（一般 6–10 份）、项目记忆放什么、哪些留在外部系统、哪些只登记不放进项目。文件骨架用 `assets/file-templates.md`。

资料如果分散在旧对话里，用 `assets/prompts.md` 里的"旧对话导出定稿"提示词，让旧对话只输出已定结论。

### 第 3 步：交叉核对文件（建项目前必做）

逐项检查，能改的直接改好，需要用户决定的列出来问：

- 编号撞车
- 和已定决策冲突（包括文件里的"建议"和已定内容不一致）
- 过时的说法
- 同一内容在几份文件里重复
- 已经发生但文件没跟上的事
- 缺少人名对照、称呼等基础信息
- 用户名下的任务是否超出他的时间预算
- 经常变的内容放错了地方

### 第 4 步：新建项目

1. 要用 GitHub 的，先确认 Claude 的 GitHub App 已装在仓库上；团队项目同时做好仓库设置（见 `references/scenarios/team-project.md`）
2. 新建项目：名称、目标（一两句话：交付物、时间、用户角色）、上下文（仓库 + Library 文件）
3. 设置：模型和思考强度、自动继续（建议见 `references/product-facts.md`）
4. 项目指令：用 `assets/project-instructions.md` 的模板，按用户情况填写

### 第 5 步：初始化项目记忆

用 `assets/prompts.md` 里的"初始化记忆"提示词，写入《决策记录》和《当前状态》，再加上一开始就该定的小约定（编号写法、称呼等）。提醒用户：占位符要换成真实内容；表格用附件发送或从纯文本编辑器复制；写完核对条数和表格是否完整。

### 第 6 步：开长期讨论串并试运行

用 `assets/prompts.md` 里的"开长期讨论串"提示词，给每个长期讨论串一个**当下真正需要的小任务**。看结果：分派得对不对、格式合不合适、有没有越权操作。不满意就改项目指令，或者让用户告诉协调器"以后这样做"。

### 第 7 步：补上运行机制

- 写一份《工作方式》（模板在 `assets/file-templates.md`）上传到 Library，并在协调器里说一次以它为准
- 让协调器设一个每天早上的定时任务生成简报
- 团队项目：把规则用简短的版本发给成员

## 维护

用户问到日常、每周、阶段结束怎么做，或者怎么更新文件时，读 `references/maintenance.md`。用户遇到问题时，先查 `references/pitfalls.md` 看是不是已知的坑。

## 每次实践后改进本 skill

一个项目运行一段时间后（或阶段结束时），用 `assets/prompts.md` 里的"让协调器复盘"提示词收集经验，然后：

1. 复盘原文去掉个人信息后，存进仓库的 `practice-logs/`
2. 能通用的经验，更新到 references 里对应的文件（产品事实注明"观察"和日期）
3. 新场景的经验写进 `references/scenarios/`，并去掉"未实践"标记
4. 在 CHANGELOG 里记一笔：版本、日期、来自哪次实践、改了什么

## 交付要求

- 给用户的文件用 Markdown，第一行写"最后更新：日期"
- 给用户的提示词放在代码块里，方便复制
- 涉及对外操作（GitHub、邮件、消息、日历）时，在项目指令里写明"不经用户确认不执行"
- 不把密钥、密码和他人的个人信息写进任何文件
